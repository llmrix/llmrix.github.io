## 第五章：模型越来越大——MoE 是怎么解决算力瓶颈的

### 一、稠密模型的天花板

第四章说到，Scaling Law 告诉我们：模型越大，效果越好。于是各家公司开始疯狂堆参数。

但很快遇到了一个现实问题：

> **模型大了，推理贵得用不起。**

一个 7B（70亿参数）的模型，生成每个词，要激活全部 70亿参数参与计算。一个 700B 的模型，每生成一个词，就要激活 7000亿参数。这意味着需要几十张高端 GPU 同时工作，成本极高。

这类每次推理都要激活所有参数的模型，叫做**稠密模型（Dense Model）**。

```
稠密模型的问题：

参数量     推理时激活参数    需要显存
7B         7B               ~16GB（单卡可跑）
70B        70B              ~140GB（需要多卡）
700B       700B             ~1400GB（需要大量卡）

参数翻10倍 → 成本翻10倍 → 没有任何节省
```

规模定律要求模型越来越大，但算力成本也等比例暴涨。这条路，走到一定程度就走不动了。

---

### 二、MoE 的核心思想：专家分工

解决思路来自一个朴素的直觉：

> **一个问题，不需要所有人都参与解决。只需要相关领域的专家来处理就够了。**

这就是 **MoE（Mixture of Experts，混合专家模型）** 的核心理念。

用一个公司来类比：

```
稠密模型 = 全员上阵

老板提出一个问题："这个产品怎么定价？"
→ 公司所有人（程序员、设计师、财务、HR、保洁）全都参与讨论
→ 大部分人其实帮不上忙，纯属浪费

MoE = 专家分工

老板提出同样的问题：
→ 路由器（Router）判断：这是定价问题
→ 只叫财务部和市场部的专家来开会
→ 其他人该干嘛干嘛，不参与
→ 同样质量的答案，开会成本大幅降低
```

把这个逻辑映射到模型架构上：

```
稠密模型每一层：
输入 → [一个大 FFN，所有参数激活] → 输出

MoE 每一层：
输入 → Router 判断 → 选 Top-K 个专家 FFN → 只激活这几个 → 输出
         ↑
    （一个小型分类器）
```

关键数字：假设有 64 个专家，每次只激活其中 2 个。总参数是稠密模型的 64 倍，但每次推理的计算量只有 2/64 ≈ 3%。

---

### 三、MoE 的结构细节

MoE 的改造，主要发生在第二章提到的 **FFN（前馈网络）** 这部分。

回忆一下：Transformer 每一层 = Self-Attention + FFN。Self-Attention 负责词间交流，FFN 负责每个词独立深化理解。FFN 占了模型参数量的大头（约 2/3）。

MoE 的做法是：**把一个大 FFN，拆成 N 个小 FFN（专家），每次只用其中 K 个。**

```
原始 Transformer 层：

token → Self-Attention → FFN（全部激活）→ 输出


MoE Transformer 层：

              ┌── Expert 1 (FFN) ──┐
              ├── Expert 2 (FFN) ──┤
token → Attn → Router → Expert 3 (FFN) → 加权合并 → 输出
              ├── Expert 4 (FFN) ──┤
              └── Expert N (FFN) ──┘
               （只激活 Top-K 个）
```

**Router 怎么选专家？**

Router 是一个很小的线性层，它接收 token 的向量，输出每个专家的"相关性分数"，然后选分数最高的 K 个专家来处理这个 token。

```
比如 token = "微积分"

Router 打分：
数学专家    → 0.82  ✅ 选中
物理专家    → 0.71  ✅ 选中
文学专家    → 0.12
历史专家    → 0.08
...

选 Top-2：数学专家 + 物理专家参与处理
```

不同的 token 会路由到不同的专家组合，每个专家逐渐"专精"于某类知识或语言模式。

---

### 四、MoE 的真实收益

用数字来感受 MoE 带来的效率提升：

```
对比：同等推理成本下能做多大的模型

稠密模型：
推理激活参数 = 总参数
想要推理成本低 → 只能把总参数做小 → 效果有限

MoE 模型（8专家选2）：
推理激活参数 = 总参数 × 2/8 = 25%
同样的推理成本 → 总参数可以做到 4 倍大 → 效果更强

MoE 模型（64专家选2）：
推理激活参数 = 总参数 × 2/64 ≈ 3%
同样的推理成本 → 总参数可以做到 32 倍大
```

这就是为什么 DeepSeek-V3 可以做到 671B 总参数，但每次推理只激活 37B——**对外宣传的推理成本，是按激活参数算的，不是总参数。**

### 五、各家的 MoE 实现对比

#### Mixtral 8x7B：让 MoE 走入大众

2023年12月，法国公司 Mistral AI 发布了 **Mixtral 8x7B**，是第一个真正意义上让开发者广泛使用的开源 MoE 模型。

```
Mixtral 8x7B 的结构：

专家数量：每层 8 个专家
每次激活：Top-2
总参数：约 47B
激活参数：约 13B（每次推理只用这么多）
效果：接近 LLaMA 2 70B，但推理成本只有一半
```

Mixtral 证明了一件事：**MoE 不只是大公司的玩具，中小团队也可以用。**

#### DeepSeek-V2：细粒度专家 + 共享专家

2024年5月，DeepSeek 发布了 V2，在 MoE 设计上做了两个重要创新：

**创新一：细粒度专家（Fine-grained Experts）**

普通 MoE：少数几个大专家（比如 8 个）
DeepSeek：大量小专家（比如 64 个），但每个专家更小

```
粗粒度 MoE：
8 个大专家，每次选 2 个 → 组合只有 28 种

细粒度 MoE（DeepSeek-V2）：
64 个小专家，每次选 6 个 → 组合有几十亿种
→ 路由更灵活，专家分工更精细
```

**创新二：共享专家（Shared Experts）**

发现有些知识是所有 token 都需要的（比如基础语法），不应该靠路由来决定要不要用。于是设置了几个"永远激活"的共享专家：

```
DeepSeek-V2 每层：

token → Router → Top-K 路由专家（按需选）  ┐
              → 共享专家（永远激活）        ┘→ 合并 → 输出
```

#### DeepSeek-V3：把 MoE 做到极致

2024年12月发布的 DeepSeek-V3，是目前开源世界 MoE 实现的天花板：

```
DeepSeek-V3 的规模：

总参数：671B
每层专家数：256 个路由专家 + 1 个共享专家
每次激活：Top-8 路由专家 + 共享专家
激活参数：约 37B

训练成本：约 558 万美元
（GPT-4 训练成本估计超过 1 亿美元）

效果：在多项基准测试上追平 GPT-4o
```

这个数字震惊了业界——**用不到 GPT-4 训练成本的 1/10，做出了接近 GPT-4 效果的模型。** MoE 的效率优势，在这里展现得淋漓尽致。

#### Qwen 的 MoE 路线

阿里的 Qwen 系列从 Qwen2.5 开始加入 MoE 版本，到 Qwen3 形成了完整的"密集版 + MoE 版"双线并行策略：

```
Qwen3 MoE（2025.04）：

总参数：235B
激活参数：22B
专家数：128 个，每次激活 8 个
特点：推理成本和 Qwen3-22B 密集版相当，
      但效果接近 Qwen3-72B 密集版
```

---

### 六、MoE 的代价：不是免费的午餐

MoE 的效率优势是真实的，但它也带来了几个新问题：

**问题一：显存占用依然按总参数算**

推理时只激活 37B 参数，但模型权重还是要全部加载到显存里。671B 的模型，权重本身就需要超过 1TB 的显存。

```
MoE 的显存矛盾：

计算量 → 按激活参数（小）
显存占用 → 按总参数（大）

→ 适合"有很多机器但每台算力不强"的分布式推理场景
→ 不适合"单机部署"
```

**问题二：专家负载不均衡**

如果 Router 总是把大量 token 路由给同几个专家，其他专家就成了"闲置员工"——参数白白占了显存，却几乎不被使用。这个问题叫**专家坍塌（Expert Collapse）**。

DeepSeek 在训练时加入了**负载均衡损失**，强迫 Router 尽量均匀分配——每个专家都要被充分使用。

**问题三：训练不稳定**

Router 的参数更新和专家的参数更新互相耦合，训练过程容易出现震荡。DeepSeek-V3 专门设计了**无辅助损失的负载均衡策略**来解决这个问题。

---

### 七、MoE 是现在，也是未来

回顾整个演进：

```
稠密模型时代（2017-2023）：
  参数量 × 10 → 效果提升，成本 × 10
  天花板：算力和成本限制了规模上限

MoE 时代（2023-至今）：
  参数量 × 10 → 效果提升，成本 × 2~3
  突破：用更低成本实现更大模型规模
```

目前业界普遍认为，未来的超大模型几乎必然是 MoE 架构。GPT-4 被广泛传言是 MoE 结构（OpenAI 未官方确认），Google 的 Gemini 1.5 也采用了 MoE。

MoE 不是一个"可选优化"，而是在模型规模继续增长的背景下，**唯一可持续的路径**。

---

### 本章小结

```
核心问题：参数越多越好，但推理成本等比例暴涨

MoE 的解法：
  把一个大 FFN → N 个小专家 FFN
  每次只激活 Top-K 个
  总参数大，激活参数小

关键数字对比：

模型             总参数   激活参数   效果
LLaMA 3 70B      70B      70B       强

核心代价：

```

MoE 解决了"模型越大越贵"的问题。但还有另一个问题在等着——**模型支持的上下文越来越长，显存又开始撑不住了。**

## 第六章：上下文越来越长——KV Cache 和注意力的进化

> **KV Cache 和注意力的进化——怎么让模型既能记住很长的内容，又不把显存撑爆。**

### 一、上下文长度为什么重要？

大模型有一个基本限制：**它每次能"看到"的文字是有上限的**，这个上限叫做**上下文窗口（Context Window）**。

早期的 GPT-3，上下文窗口只有 2048 个 token（大约 1500 个汉字）。这意味着：
- 给它一篇长文章，超出部分直接看不到
- 对话太长，早期内容会被截断遗忘
- 无法处理整本书、整份代码库

但真实的应用场景里，长上下文至关重要：

```
需要长上下文的场景：

法律合同审查    → 一份合同几万字
代码库分析      → 整个项目的所有文件
长对话记忆      → 几十轮对话不忘前文
学术论文理解    → 论文+参考文献一起读
书籍摘要        → 一本书十几万字
```

于是各家开始疯狂扩展上下文长度：

```
上下文长度的演进：

GPT-3（2020）      2K tokens
GPT-4（2023）      8K → 32K → 128K
Claude 3（2024）   200K tokens
Gemini 1.5（2024） 1M tokens
Gemini 1.5 Pro     2M tokens
```

但上下文越长，背后的代价越大。理解这个代价，就要先理解 **KV Cache**。

---

### 二、KV Cache 是什么？

回忆第二章：Transformer 的 Self-Attention 里，每个词会生成三个向量：Q（查询）、K（键）、V（值）。

在**推理阶段**（也就是模型生成文字的时候），有一个关键特点：

> 模型每次只生成一个新 token，但每生成一个新 token，都需要跟前面**所有已生成的 token** 做注意力计算。

如果每次都从头重新计算所有 token 的 K 和 V，就会有大量重复计算——前面 token 的 K、V 值根本没变，为什么要重算？

**KV Cache 的思路**：把已经计算过的 K 和 V 缓存起来，下次直接用，不重新计算。

```
没有 KV Cache：

生成第 100 个词时：
重新计算 token 1~99 的 K、V → 大量重复计算

有 KV Cache：

生成第 100 个词时：
直接读取缓存的 token 1~99 的 K、V → 只计算新 token 的 K、V
```

KV Cache 用**空间换时间**，大幅提升了推理速度。几乎所有推理框架都会默认开启它。

**但代价是显存。**

---

### 三、KV Cache 的显存危机

KV Cache 缓存的内容有多大？

```
KV Cache 的大小 ≈ 层数 × 头数 × 序列长度 × 每个值的大小

以 LLaMA 2 70B 为例：
层数：80 层
注意力头数：64 个头（K 和 V 各一套）
序列长度：4096 tokens
精度：FP16（每个数 2 字节）

KV Cache 大小 = 80 × 2 × 64 × 4096 × 128 × 2 字节
              ≈ 10.7 GB

这还只是 4K 上下文。如果是 128K 上下文：
≈ 10.7 GB × 32 ≈ 342 GB
```

342GB 的 KV Cache，已经超过了大多数 GPU 集群的总显存。

更直观地说：

```
上下文越长 → KV Cache 越大 → 显存越不够用

序列长度翻倍 → KV Cache 也翻倍
序列长度 × 10 → KV Cache × 10

这是线性增长，但实际推理中，上下文动辄从 4K 增长到 128K，
也就是 32 倍——KV Cache 从 10GB 涨到 342GB。
```

这就是为什么长上下文是个真正的工程难题，不是"把窗口数字改大"就能解决的。

---

### 四、从 MHA 到 MQA 到 GQA：共享 KV 的三代演变

既然 KV Cache 太大，最直接的思路是：**能不能减少需要缓存的 K、V 数量？**

#### 第一代：MHA（Multi-Head Attention）——原始设计

第二章讲过，原始 Transformer 用多头注意力，每个头都有自己独立的 Q、K、V。

```
MHA（假设 8 个头）：

Head 1: Q1, K1, V1
Head 2: Q2, K2, V2
Head 3: Q3, K3, V3
...
Head 8: Q8, K8, V8

KV Cache 需要缓存：K1~K8, V1~V8 → 16 份数据
```

8 个头，就要缓存 16 份（8个K + 8个V）。头越多，缓存越大。

#### 第二代：MQA（Multi-Query Attention）——激进压缩

2019年 Google 提出了 MQA：**所有头共享同一套 K 和 V，只有 Q 各自独立。**

```
MQA（8 个头）：

Head 1: Q1, K, V  ┐
Head 2: Q2, K, V  │
Head 3: Q3, K, V  ├─ 所有头共用同一个 K 和 V
...               │
Head 8: Q8, K, V  ┘

KV Cache 需要缓存：K, V → 只需 2 份数据（从 16 份压缩到 2 份）
```

KV Cache 缩小了 8 倍，推理速度大幅提升。

但代价是：**效果有所下降。** 所有头共用一套 K、V，意味着它们"看"信息的角度被强制统一，多头注意力的多样性优势打了折扣。

#### 第三代：GQA（Grouped Query Attention）——折中方案

2023年 Google 提出 GQA，介于 MHA 和 MQA 之间：**把多个头分成若干组，同组内共享 K、V。**

```
GQA（8个头，分成4组，每组2个头）：

组1: Q1, Q2 → 共享 K1, V1
组2: Q3, Q4 → 共享 K2, V2
组3: Q5, Q6 → 共享 K3, V3
组4: Q7, Q8 → 共享 K4, V4

KV Cache 需要缓存：K1~K4, V1~V4 → 8 份数据
（从 MHA 的 16 份 压缩到 8 份，从 MQA 的 2 份 扩展到 8 份）
```

GQA 在压缩率和效果之间找到了平衡点，成为目前开源模型的主流选择：

```
采用 GQA 的主流模型：

LLaMA 2/3    ✅ GQA
Qwen 2/3     ✅ GQA
Mistral      ✅ GQA
Gemma        ✅ GQA
```

---

### 五、MLA：DeepSeek 的真正创新

GQA 是目前的主流，但 DeepSeek 在 V2 里提出了一个更激进的方案——**MLA（Multi-head Latent Attention，多头潜在注意力）**。

GQA 的思路是"减少 K、V 的份数"。MLA 的思路完全不同：

> **不存完整的 K、V，而是存一个高度压缩的"潜向量"，需要时再解压。**

用一个类比来理解：

```
GQA 的做法：
原来存 10 份文件，现在合并成 4 份
→ 节省了存储，但文件内容没有压缩

MLA 的做法：
把 10 份文件全部压缩打包成 1 个压缩包
→ 需要用哪份文件，临时解压出来
→ 存储大幅减少，用的时候多一步解压
```

具体来说：

```
传统注意力（MHA/GQA）缓存：
每个 token → 缓存完整的 K 向量 + 完整的 V 向量

MLA 缓存：
每个 token → 只缓存一个低维"潜向量"c
需要时：c → 解压 → K 和 V

潜向量的维度远小于完整的 K+V
→ KV Cache 大幅缩小
```

实际效果：

```
DeepSeek-V2 的数据：

MHA：KV Cache 大小 = 基准 100%
GQA：KV Cache 大小 ≈ 25%（减少 75%）
MLA：KV Cache 大小 ≈ 7%（减少 93%）

MLA 比 GQA 还能再节省约 70% 的 KV Cache
```

同时，MLA 保留了完整的多头注意力表达能力——因为解压之后仍然是完整的 K、V，计算质量不打折。

这就是为什么说 MLA 是真正的结构创新，而不只是工程 trick：**它在不损失效果的前提下，把 KV Cache 压缩到了极致。**

---

### 六、位置编码的演进：RoPE 是怎么让模型突破长度限制的

解决了 KV Cache 的显存问题，还有另一个难题：**模型训练时只见过 4K 长度的序列，推理时遇到 128K 长度的输入，怎么办？**

这涉及到**位置编码**的问题。

第二章说到，Transformer 用位置编码告诉模型"每个词在第几位"。最初的设计是固定的正弦函数，对长度泛化很差——训练时没见过的位置，推理时就不知道怎么处理。

**RoPE（Rotary Position Embedding，旋转位置编码）** 是 LLaMA 采用的方案，它的核心思想是：

> **不直接给词加位置信息，而是在计算注意力时，通过旋转 Q 和 K 的向量来隐式表达位置关系。**

```
传统位置编码：
词向量 = 语义向量 + 位置向量（直接相加）
→ 位置信息固化在向量里，超出训练长度就乱了

RoPE：
计算注意力时：Q 和 K 根据各自位置旋转一个角度
→ 两个词的注意力分数，自然地包含了它们的相对距离信息
→ 位置信息是"动态的"，而不是固化在权重里
```

RoPE 的优势在于它对位置的表达是**相对的**——模型学到的是"词 A 和词 B 相差 N 个位置时的关系"，而不是"词 A 在绝对位置 100"。

这使得 RoPE 天然具备一定的外推能力。

**但直接外推还是不够**，训练时只见过 4K，推理时遇到 32K，旋转角度超出了训练范围，效果会下降。

于是出现了各种 **RoPE 外推技术**：

```
主要的 RoPE 外推方案：

方案              原理                        代表
线性插值          把长序列"压缩"到训练长度内    LLaMA 2 Long
YaRN             动态调整旋转频率              Mistral、Qwen
LongRoPE         分段调整，不同位置不同策略    Phi-3
ABF（基频调整）   调整 RoPE 的基础频率参数      LLaMA 3
```

LLaMA 3 用了 ABF 配合长文本继续训练，把上下文从 8K 扩展到了 128K，是目前比较成熟的工业级方案。

---

### 七、超长上下文的终极方案：Ring Attention

当上下文长到百万级别（Gemini 1.5 的 1M tokens），单张卡或少数几张卡已经完全放不下了。

这时候需要更激进的方案：**Ring Attention（环形注意力）**。

思路是把序列切片，分配到多张 GPU 上，每张卡只处理一段，然后让所有卡像"接力传球"一样，循环交换必要的信息：

```
Ring Attention（4张卡处理超长序列）：

序列：[token 1~250K] [token 250K~500K] [token 500K~750K] [token 750K~1M]
         GPU 1            GPU 2             GPU 3             GPU 4
           ↓                ↓                 ↓                 ↓
        处理本段          处理本段           处理本段           处理本段
           ↓                ↓                 ↓                 ↓
        ←←←←←←←←←← 环形传递 KV 信息 →→→→→→→→→→→→→→→→→→
```

每张卡在处理自己这段序列的同时，把自己的 KV 传给下一张卡，同时接收上一张卡的 KV。所有卡跑完一圈，每段 token 就看到了全部序列的信息。

这是 Gemini 1.5 实现 1M 上下文的关键工程技术之一。

---

### 本章小结

```
核心问题：上下文越长，KV Cache 越大，显存越爆

三代注意力演进：

MHA  → 每个头独立 K、V  → KV Cache 最大，效果最好
MQA  → 所有头共享 K、V  → KV Cache 最小，效果有损
GQA  → 分组共享 K、V    → 折中，成为主流（LLaMA/Qwen）

MLA（DeepSeek 创新）：
  → 缓存低维潜向量，按需解压
  → KV Cache 比 GQA 再降 70%，效果无损

位置编码演进：
  正弦编码 → RoPE → YaRN/LongRoPE/ABF
  → 从固定长度 → 可外推到更长序列

超长上下文：
  Ring Attention → 多卡环形传递，实现百万 token 级别

各方案对比：

技术          KV Cache    效果    代表模型
MHA           100%        最好    早期 GPT
GQA           ~25%        接近    LLaMA 3、Qwen3
MLA           ~7%         接近    DeepSeek-V2/V3
```

KV Cache 的问题解决了，上下文也能做长了。但还有一个更根本的问题浮现：

**模型再大、上下文再长，它每次都是"一步出答案"的——它不会停下来想一想。** 这是下一代能力的天花板。

---

## 第七章：模型开始"思考"——Reasoning 架构的出现

> **模型开始"思考"——Reasoning 架构是怎么让模型学会先想再答的。**

### 一、一个根本性的问题

前六章解决的都是"怎么让模型更大、更快、更长"的问题。但到了2024年，研究者发现了一个更根本的天花板：

> **数据快用完了。**

Scaling Law 告诉我们：更多数据 + 更多参数 = 更好效果。但互联网上的高质量文本是有限的。有研究估计，到2024-2025年，人类能用于训练的高质量文字数据已经接近枯竭。

继续堆数据这条路，快走到头了。

那怎么继续让模型变得更聪明？

答案来自一个反直觉的方向：**不在训练时花更多，而在推理时花更多。**

> **与其把模型训练得"答案更准"，不如让模型在回答之前"想得更多"。**

这就是 **Test-time Compute（推理时计算）** 的核心思想，也是 Reasoning 架构的出发点。

---

### 二、普通模型是怎么回答问题的？

要理解 Reasoning 架构的变化，先要清楚普通模型是怎么工作的。

普通的大模型，回答问题的过程是这样的：

```
用户：  1234 × 5678 等于多少？

模型：  直接预测下一个 token → 7006652

整个过程：
输入问题 → [模型内部一次前向计算] → 直接输出答案
```

这叫**一步推理**——模型接收问题，在一次前向传播中直接生成答案，没有任何中间步骤。

这对简单问题没什么问题。但对复杂的推理任务——数学证明、逻辑推断、代码调试——一步出答案的方式，正确率非常不稳定。

为什么？因为复杂问题本质上需要**多步推导**，每一步都依赖上一步的结论。如果模型没有显式的中间步骤，就相当于要它在脑子里同时完成所有推导，容易出错。

---

### 三、Chain of Thought：让模型"说出思考过程"

2022年，Google 研究者发现了一个简单但有效的技巧：**在提示词里加入思维链示例，让模型先写出推理过程，再给出答案。**

```
普通提示：
Q: 小明有 5 个苹果，给了小红 2 个，又买了 3 个，现在有几个？
A: 6 个

思维链提示（CoT）：
Q: 小明有 5 个苹果，给了小红 2 个，又买了 3 个，现在有几个？
A: 小明开始有 5 个。
   给了小红 2 个，还剩 5-2=3 个。
   又买了 3 个，现在有 3+3=6 个。
   答案是 6 个。
```

仅仅是让模型"写出步骤"，复杂推理任务的正确率就大幅提升。

原因也直觉：**中间步骤成了"草稿纸"**，每一步的结论作为下一步的输入，模型不需要在一次计算里完成所有推导。

但 CoT 还只是个提示技巧，思维链是人工设计的示例触发的，不是模型真正学会了"思考"。

---

### 四、o1：把思考链内化进模型

2024年9月，OpenAI 发布了 **o1**，这是第一个真正把"思考"变成模型原生能力的产品。

o1 的行为和普通模型有一个肉眼可见的区别：

```
普通 GPT-4：
用户提问 → 立刻开始输出答案（几乎无延迟）

o1：
用户提问 → [thinking...] → 经过几秒到几十秒 → 输出答案
```

这个 `[thinking...]` 阶段，模型在生成大量内部"思考 token"——它在用自然语言推演解题过程，就像人类在草稿纸上演算一样。

```
o1 的内部思考（简化示意）：

用户：证明根号2是无理数

[thinking]
让我用反证法来证明。
假设根号2是有理数，那么可以写成 p/q 的形式，其中 p、q 互质...
两边平方得 2 = p²/q²，即 2q² = p²...
这说明 p² 是偶数，所以 p 是偶数，设 p = 2k...
代入得 2q² = 4k²，即 q² = 2k²...
这说明 q 也是偶数，与 p、q 互质矛盾...
[/thinking]

输出：用反证法。假设根号2 = p/q（最简分数）...
```

思考 token 对用户通常是隐藏的（或折叠显示），但它们是真实计算的一部分，消耗真实的算力。

**思考越多，答案越准——但也越贵、越慢。**

---

### 五、为什么"多想"能让模型更聪明？

这背后有一个深刻的道理：

> **生成 token 的过程，本身就是一种计算。**

模型每生成一个 token，都要做一次完整的前向传播——经过所有层的注意力和 FFN 计算。

```
生成 100 个 token：做 100 次前向传播
生成 1000 个 token：做 1000 次前向传播

思考 token 越多 → 做的计算越多 → 推理能力越强
```

这就好比让一个数学家解题：
- 不打草稿，直接写答案 → 只适合简单题
- 打草稿，逐步推演 → 能解决复杂题
- 草稿纸用得越多，能解决的题越难

对模型来说，思考 token 就是草稿纸，而草稿纸的"面积"（token 数量）直接决定了能解决多复杂的问题。

这个范式被称为 **Test-time Compute Scaling**——在推理阶段投入更多计算，换取更好的结果。

---

### 六、怎么训练出会"思考"的模型？

o1 的训练细节 OpenAI 没有完全公开，但从 DeepSeek-R1 的开源论文里，我们能看清楚这件事的基本逻辑。

**关键转变：从模仿到自我强化**

普通模型的训练（SFT，监督微调）：
```
给模型看大量"问题→正确答案"的示例
模型学会模仿这些示例
→ 模型学的是"怎么写"，不是"怎么想"
```

Reasoning 模型的训练核心是**强化学习（RL）**：
```
让模型自己尝试解题
检查答案对不对（数学题可以精确验证）
答对了 → 这条推理路径得到奖励
答错了 → 这条推理路径被惩罚
→ 模型逐渐学会"哪种思考方式更容易得到正确答案"
```

**DeepSeek-R1 的关键：GRPO**

DeepSeek-R1 用了 **GRPO（Group Relative Policy Optimization）** 替代了更复杂的 PPO 算法：

```
传统 PPO 的问题：
需要训练一个额外的"评分模型"来判断回答好不好
→ 训练成本高，容易不稳定

GRPO 的做法：
对同一个问题，让模型生成多个不同的回答
把这些回答互相比较，好的得正分，差的得负分
→ 不需要额外评分模型，训练更简单稳定
```

```
GRPO 示例：

问题："解方程 2x + 3 = 7"

模型生成 8 个回答：
回答1：x = 2（正确） ↑ 加分
回答2：x = 2（正确） ↑ 加分
回答3：x = 5（错误） ↓ 减分
回答4：x = 2（正确） ↑ 加分
...

用这批回答的相对好坏来更新模型参数
→ 正确推理路径的概率提高
→ 错误推理路径的概率降低
```

---

### 七、各家 Reasoning 模型的行为对比

Reasoning 架构带来的能力变化，在行为上非常明显：

**OpenAI o1/o3**

```
特点：
- 思考过程完全隐藏（用户看不到）
- 思考时间从几秒到几分钟不等
- 数学、代码、逻辑推理大幅领先普通模型
- 成本比 GPT-4o 高 3~10 倍

典型场景：
- 竞赛级数学题（AMC、AIME）
- 复杂代码调试
- 多步逻辑推理
```

**DeepSeek-R1**

```
特点：
- 思考过程完全可见（用户能看到模型在想什么）
- 完全开源，可本地部署
- 效果追平 o1，训练成本极低
- 思考链有时候会"自言自语"很长

亮点：
模型会在思考中出现"等等，我刚才算错了，重新来"
这种自我纠错行为是自发涌现的，没有人专门教它
```

**Qwen3 的思考模式切换**

```
Qwen3 的设计比较独特：

非思考模式（/no_think）：
  → 直接回答，速度快，适合简单问题

思考模式（/think）：
  → 开启内部推理，适合复杂问题

用户可以手动控制，或者模型自动判断用哪种模式
→ 在效果和成本之间灵活权衡
```

**Claude 3.7 Sonnet 的扩展思考**

```
Claude 的方案叫"Extended Thinking"：
- 可以设置思考预算（thinking budget）
- 告诉模型最多用多少 token 来思考
- 预算越高，模型想得越仔细，但也越慢越贵
- 适合需要精确控制成本/效果的场景
```

---

### 八、Reasoning 模型还没解决的问题

Reasoning 架构带来了巨大的能力提升，但也引入了新问题：

**过度思考（Overthinking）**

```
简单问题："1+1等于多少？"

Reasoning 模型可能的回答：
[thinking]
让我仔细考虑这个问题。1+1在十进制下...
在不同数制下结果可能不同...
在布尔代数中1+1=1...
在模2算术中1+1=0...
在通常的整数算术中...
[/thinking]
答案是：2

→ 花了大量 token 思考一个根本不需要想的问题
→ 成本浪费，速度慢
```

**思维链幻觉**

```
模型的思考过程看起来很严谨，但推理链里可能藏着错误：

[thinking]
已知 A > B，B > C，所以 A > C ✅
已知 X 是偶数，所以 X² 是偶数 ✅
已知...（中间某步悄悄出错）...
所以最终答案是 42 ❌

→ 表面上是"有推理过程"，实际结论仍然错误
→ 用户看到长长的思考链，反而更容易轻信错误答案
```

**不可验证性——以及当前的应对思路**

对于没有标准答案的问题（写作、创意、开放性分析），强化学习的"对错奖励"无法直接应用，Reasoning 架构的优势大打折扣。

这是目前业界最难解决的问题之一，当前有几条并行的探索路径：

```
路径一：奖励模型（Reward Model）
  训练一个专门的"评委模型"对回答质量打分
  → 替代人工评分，规模化可行
  → 问题：容易被主模型"钻空子"（回答越长分越高）
    导致堆砌内容而非真正提升质量

路径二：宪法 AI（Anthropic）
  写一套原则（诚实、无害、有帮助），让模型对照原则
  自我批评并修改，再用修改前后的对比训练奖励模型
  → 减少人工标注，原则可显式控制
  → 局限：能管安全和帮助性，管不了"创意好不好"

路径三：过程奖励模型（PRM）
  不只对最终答案打分，对推理链的每一步单独打分
  → 即使没有标准答案，也能评判"逻辑是否清晰"
  → 现状：标注成本极高，目前主要用于数学/代码

路径四：自我批评与迭代精炼
  模型生成 → 模型批评 → 模型修改，循环多轮
  → 代码任务有效（运行结果提供客观反馈）
  → 写作任务效果有限（批评和修改来自同一模型，盲点相同）

路径五：多模型辩论
  多个模型实例互相评判，模拟同行评审
  → 学术上验证有效，产品落地成本高（推理成本 3~5 倍）
```

**一句话现状**：对真正开放的创意和写作任务，目前没有像数学题那样干净的解法。主流做法是用奖励模型 + 大量人类偏好数据来近似——本质是训练模型"更像人类喜欢的样子"，而不是"更有创意"，这两件事并不等价。

---

### 本章小结

```
核心问题：数据快用完了，继续堆规模的路变窄了

Reasoning 的解法：
  不在训练时花更多 → 在推理时花更多
  让模型生成"思考 token" → 用计算换准确率

演进路径：
CoT（2022）
  └─ 提示技巧，人工设计示例触发思维链

o1（2024.09）
  └─ 思考链内化，强化学习训练
  └─ Test-time Compute Scaling 范式确立

DeepSeek-R1（2025.01）
  └─ 开源，GRPO 训练，思考过程可见
  └─ 自我纠错行为自发涌现

Qwen3 / Claude 3.7
  └─ 思考模式可切换 / 思考预算可控制
  └─ 在效果和成本间灵活权衡

核心代价：
- 推理变慢（思考需要时间）
- 成本变高（思考消耗 token）
- 过度思考问题尚未解决
- 开放性问题效果有限
```

Reasoning 架构让模型学会了"想"。但还有一个维度的能力是缺失的：**模型只能处理文字，看不到、听不到真实世界。**

下一章：**模型开始"看世界"——多模态架构是怎么让模型理解图片、音频和视频的。**

## 第八章：模型开始"看世界"——多模态架构的演进

### 一、语言之外的世界

前七章讲的所有架构，处理的都是**文字**。但真实世界不只有文字——人类理解世界，靠的是视觉、听觉、触觉共同配合。

一个只懂文字的模型，遇到这些场景就完全失效：

```
纯语言模型处理不了的任务：

"帮我看看这张 X 光片有没有异常"      → 不认识图片
"这段视频里的人在做什么"             → 不认识视频
"这首歌是什么风格"                   → 不认识音频
"帮我识别这张发票上的金额"           → 不认识图片
"这个电路板的焊点有问题吗"           → 不认识图片
```

让模型理解图片、音频、视频，就是**多模态**要解决的问题。

但不同模态的数据，格式天差地别：

```
文字：离散的 token 序列       [我, 爱, 北京]
图片：连续的像素矩阵          [H×W×3 的数字阵列]
音频：连续的波形采样           [时间序列的振幅值]
视频：图片序列 + 音频          [T×H×W×3 + 波形]
```

怎么让一个模型同时理解这些完全不同格式的输入？这就是多模态架构要回答的问题。

---

### 二、第一代方案：视觉编码器作为"翻译官"

最早的思路很直接：**既然语言模型只懂 token，那就把图片"翻译"成 token。**

具体做法是引入一个独立的**视觉编码器（Visual Encoder）**，专门负责把图片转换成语言模型能理解的向量。

```
第一代多模态架构：

图片
 ↓
视觉编码器（独立训练）
 ↓
图像特征向量
 ↓
投影层（把图像向量对齐到语言空间）
 ↓
语言模型（正常处理 token）
 ↓
文字输出
```

最常用的视觉编码器是 **对比语言 - 图像预训练(CLIP)**（OpenAI，2021年）。CLIP 用海量"图片-文字"对训练，学会了把图片和对应的文字描述映射到同一个向量空间——也就是说，"一只猫的图片"和"一只猫"这段文字，在 CLIP 的向量空间里是相邻的。

```
CLIP 的核心能力：

图片"一只橘猫坐在窗边" → 向量 [0.3, 0.7, ...]
文字"一只橘猫坐在窗边" → 向量 [0.3, 0.7, ...]

两个向量几乎相同 → 图片和文字对齐了
```

有了 CLIP，接一个投影层，再接语言模型，就能做图文理解了。

这个方案的代表：
```
早期多模态模型：

LLaVA（2023）
  → CLIP + 投影层 + LLaMA
  → 开源社区第一个实用的多模态模型

MiniGPT-4（2023）
  → CLIP + Q-Former + Vicuna
  → 同样是"外挂视觉编码器"的思路

mPLUG-Owl（2023）
  → 阿里团队，中文多模态
```

### 三、插件式的瓶颈

"视觉编码器 + 语言模型"这个方案能用，但有几个根本性的限制：

**限制一：视觉编码器是冻结的**

CLIP 是单独预训练好的，接到语言模型上之后，通常保持不变（冻结参数）。这意味着视觉编码器只会提取它在预训练时学到的特征，而不能根据语言模型的需求进行调整。

```
比喻：
就像请了一个只会说英语的翻译官，把图片"翻译"成描述，
再给只会说中文的人听。
翻译官的理解能力是固定的，
如果图片里有一些专业知识，翻译官不懂，就翻译不准。
```

**限制二：图像 token 数量爆炸**

一张 224×224 的图片，经过 CLIP 的 patch 切分，会产生 196 个图像 token。一张高清图（1024×1024）则产生超过 4000 个 token。

这些图像 token 和文字 token 一起塞进语言模型，上下文窗口很快就被图片占满了。

```
1 张高清图 ≈ 4000 token ≈ 3000 个汉字

如果要处理一段 10 秒的视频（每秒 24 帧）：
240 帧 × 4000 token/帧 = 96 万 token

这已经超过了大部分模型的上下文限制
```

**限制三：视觉和语言是割裂的**

视觉编码器和语言模型是两个独立训练的系统，中间只靠一个投影层连接。这种"拼接"的方式，导致两个模块之间的理解不够深度融合。

---

### 四、第二代方案：深度融合

为了解决插件式的问题，研究者开始尝试让视觉和语言更深度地融合。

#### Q-Former：用查询向量做桥梁

**BLIP-2**（Salesforce，2023）提出了 Q-Former 结构：不是直接把视觉特征丢给语言模型，而是先用一组"查询向量"去从图片里提取最关键的信息。

```
Q-Former 的工作方式：

图片 → 视觉编码器 → 大量图像特征

Q-Former 里有 32 个可学习的"查询向量"
这些查询向量去"询问"图像特征：
"你里面有哪些对语言理解最有用的信息？"

→ 32 个向量提炼出图片的精华
→ 只把这 32 个向量传给语言模型（而不是几千个原始图像 token）

好处：大幅压缩了图像 token 数量
```

#### 动态分辨率：按需分配 token

另一个重要改进是**动态分辨率**——根据图片内容决定用多少 token 来表示它：

```
简单图片（纯色背景 + 一个物体）：
→ 用少量 token 就够了，不需要细节

复杂图片（密密麻麻的文字、精细的图表）：
→ 需要大量 token 才能捕捉细节

动态分辨率的做法：
把图片切成多个小块，每块单独编码
简单区域：少切几块
复杂区域：多切几块

代表：InternVL 2、Qwen-VL
```

### 六、视频理解：帧数爆炸怎么解决

视频是多模态里最难处理的模态，原因很简单：

```
视频 = 图片序列 + 音频

1 秒视频（24帧）× 每帧 1000 token = 24000 token
1 分钟视频 = 1,440,000 token ← 远超任何模型的上下文

即使是 Gemini 的 100 万 token，
也只够装大约 40 秒的高清视频。
```

目前解决视频理解的主要思路：

**思路一：抽帧采样**
```
不处理每一帧，而是每隔 N 帧取一帧
1 分钟视频 → 每秒取 1 帧 → 60 帧 → 约 60000 token
→ 丢失了大量细节，适合"大致理解内容"
```

**思路二：视频专用编码器压缩**
```
不把每帧都展开成 token
而是用专门的视频编码器提取时序特征
把连续帧压缩成更少的"视频 token"

代表：Qwen2-VL 的 3D 卷积时序压缩
→ 相邻帧的相似内容合并压缩
→ 大幅减少 token 数量
```

**思路三：滑动窗口处理**
```
把长视频切成多个短片段
每段单独理解
最后汇总各段的理解
→ 适合长视频摘要类任务
```

### 七、音频：语音理解的统一化

音频的处理路径和图像类似，但有一个关键的里程碑：**Whisper（OpenAI，2022）**。

Whisper 是一个强大的语音识别模型，它的存在让"把语音转成文字，再给语言模型处理"变得极其容易。

```
早期语音处理：
语音 → Whisper → 文字 → 语言模型 → 回答
（两个独立模型串联，有延迟）

GPT-4o 的语音处理：
语音 → 统一 tokenizer → 语言模型 → 语音/文字输出
（端到端，延迟极低，能感知语气和情绪）
```

GPT-4o 的实时语音能力是一个重要里程碑——它不再是"先转文字再处理"，而是直接把语音作为输入模态，这使得它能感知说话人的情绪、语气、停顿，甚至背景音。

### 八、多模态的下一步：统一生成

目前大多数多模态模型只能**输入**多模态（看图、听音频），但**输出**只有文字。

下一个方向是**多模态输出**——模型不只是理解图片，还能直接生成图片：

```
当前主流：
输入：图片 + 文字
输出：文字

下一步目标：
输入：图片/音频/视频/文字（任意组合）
输出：图片/音频/视频/文字（任意组合）

已有进展：
Gemini 2.0   → 原生支持图片生成输出
GPT-4o       → 支持图片输出（2025年初开放）
```

实现统一生成的关键，是把图像生成也变成"预测 token"的问题——把图片用离散的视觉 token 表示，和文字 token 放在同一个序列里一起训练。

这个方向还在快速发展中。
