# 九、评估体系

评估体系的质量直接决定模型迭代的方向和速度。没有可靠的评估，优化就是盲目的。

---

## 9.1 评估方法论

### 三种评估方式

**自动评估（Automatic Evaluation）：**
用预定义的指标（准确率、BLEU、ROUGE、pass@k）自动评分。速度快、成本低、可复现，但对开放式任务覆盖不足。

**人工评估（Human Evaluation）：**
由人工评估员对模型回答进行评分或排序。最接近真实用户体验，但成本高、速度慢、主观性强。

**LLM-as-Judge（模型评估模型）：**
用强大的语言模型（如 GPT-4）评估被测模型的输出。成本和速度介于自动评估和人工评估之间，已被广泛验证与人工评估结论高度相关。

注意：LLM-as-Judge 存在"位置偏差"（倾向于选择第一个答案）和"长度偏差"（倾向于选择更长的答案）。应使用双向比较（A vs B 和 B vs A 各做一次）来消除位置偏差。

### 评估流程设计原则

1. **评估集与训练集严格分离**：任何在训练中出现过的数据都不能用于评估
2. **固定评估集**：每次迭代用相同的评估集，才能比较不同版本的模型
3. **多维度覆盖**：单一 benchmark 无法全面反映模型能力，至少覆盖知识、推理、代码等核心维度
4. **定期刷新**：当模型在某个 benchmark 接近满分时，该 benchmark 已失去区分度，需要引入更难的评估集

---

## 9.2 能力维度评测

### 知识理解

**MMLU（Massive Multitask Language Understanding）：**
涵盖 57 个学科（数学、历史、法律、医学……）的选择题，共约 15,000 道题。是最广泛使用的知识评估 benchmark。

**C-Eval：** 中文版 MMLU，涵盖 52 个学科，专门评估中文知识能力。中文模型的标配评估集。

### 数学推理

**GSM8K：** 约 8,500 道小学数学应用题，需要多步推理。GPT-3.5 约 57%，GPT-4 约 92%，o1 接近满分。

**MATH：** 高中竞赛数学题，共 12,500 道，难度远高于 GSM8K。这是当前顶级模型仍在努力突破的难关之一。

**BBH（BIG-Bench Hard）：** 从 BIG-Bench 中筛选出的 23 个特别难的任务，涵盖逻辑推理、因果推断等复杂能力。

### 代码能力

**HumanEval：** OpenAI 发布的代码生成 benchmark，164 道 Python 编程题，用 pass@1（一次通过率）评估。

**MBPP（Mostly Basic Python Problems）：** 974 道基础 Python 题，难度低于 HumanEval，适合评估基础代码能力。

### 长上下文

**Needle-in-a-Haystack（大海捞针）：** 在超长文档中插入一句关键信息，测试模型能否在不同位置找到它。直观显示模型在不同上下文位置的注意力能力。

**RULER：** 更系统化的长上下文评估，包括多针检索、信息聚合等多种任务。

---

## 9.3 对齐与安全评测

**MT-Bench：** 80 道多轮对话题，使用 GPT-4 作为评委打分（1-10 分）。覆盖写作、推理、数学、代码、角色扮演等 8 个类别。

**IFEval（Instruction Following Evaluation）：** 评估模型对具体指令的遵从能力，如"回答不超过 100 字"、"用列表格式回答"等可验证约束。

**TruthfulQA：** 817 道"容易让人说谎"的问题，测试模型是否会输出虚假但听起来合理的内容（幻觉）。

**红队测试（Red Teaming）：** 系统性地尝试各种攻击方式（角色扮演绕过、越狱提示、多语言绕过……），找出模型的安全弱点。通常需要专业安全团队执行。

---

## 9.4 评测陷阱与反思

### Benchmark 饱和

当所有主流模型在某个 benchmark 上都接近满分，这个 benchmark 就失去了区分度。例如 GSM8K 已几乎被顶级模型"刷满"，MATH 正在接近这个状态。

**应对方法：** 持续引入更难的 benchmark（AIME、GPQA Diamond 等），或构建动态更新的评估集。

### 数据污染

如果测试题目出现在训练集中，模型可能记住了答案而非真正理解，导致评分虚高。

**识别方法：**
- n-gram 重叠检测：检查测试题与训练数据的文本相似度
- 逐字匹配：检查测试题是否完全出现在训练数据中
- 变体测试：将题目稍作修改，如果分数急剧下降，说明模型在"背题"

### 评测分数高但体验差

这是实际工程中最常见的陷阱。模型可能在所有 benchmark 上得分很高，但：
- 回答冗长啰嗦，不直接回答问题
- 拒绝过于保守，很多正常请求也拒绝
- 中文能力强但输出混入大量英文
- 单轮表现好但多轮对话衰退

**根本原因：** 标准 benchmark 无法覆盖真实使用场景的所有维度。

## 9.5 实践选型建议

### 最小评估集推荐

对于资源有限的团队，以下 5 个 benchmark 可以覆盖核心能力维度：

| Benchmark | 评测维度 | 重要性 |
|-----------|---------|-------|
| MMLU | 通用知识 | ★★★★★ |
| GSM8K 或 MATH | 数学推理 | ★★★★★ |
| HumanEval | 代码能力 | ★★★★☆ |
| MT-Bench | 指令跟随/对话 | ★★★★☆ |
| C-Eval（中文模型必选）| 中文知识 | ★★★★★ |

### 内部评测集构建方法

业务落地**必须**构建领域内部评测集：

1. **收集真实用户问题**：从产品日志中采样 100-200 个典型问题
2. **人工标注黄金答案**：为每道题写出"理想回答"或评分标准
3. **覆盖边缘场景**：包含一些刁钻问题、安全边界测试
4. **设计自动评分规则**：能自动评分的尽量自动（如关键词检查），无法自动的用 LLM-as-Judge

内部评测集 100-500 条即可，**比任何标准 benchmark 都更能反映模型在你的业务上的实际表现**。

### 持续评估建议

- **训练过程中**：每 1000-5000 steps 在验证集上评估一次 loss，每 10% 进度做一次完整 benchmark 评估
- **每次发布前**：完整跑一遍所有 benchmark + 内部评测集
- **版本间比较**：记录每个 checkpoint 的所有指标，建立模型能力档案

# 十、推理部署与工程基础设施

训练好的模型需要服务真实用户，这时候的核心矛盾变成了：**如何用最低的成本，服务尽可能多的用户，同时保证足够低的响应延迟**。

---

## 10.1 推理引擎选型

| 引擎 | 适用场景 | 核心技术 | 定位 |
|------|---------|---------|------|
| **vLLM** | 高并发在线服务 | PagedAttention | 大多数场景的首选 |
| **TensorRT-LLM** | NVIDIA GPU 极致性能 | 算子融合、INT8/FP8 | 延迟敏感场景的性能天花板 |
| **llama.cpp** | 端侧/本地/CPU 推理 | GGUF + 量化 | 个人部署、边缘设备 |
| **SGLang** | 复杂推理流程/Agent | RadixAttention | 多轮对话、Agent 场景 |

### vLLM：在线服务的事实标准

传统 KV Cache 管理会浪费大量显存——每个请求预先分配最大长度的连续内存块，但实际生成长度往往远短于此，导致大量内存碎片。

PagedAttention 将 KV Cache 分成固定大小的"页"按需分配，不同请求还可以共享相同前缀的 KV Cache（Prefix Caching），大幅提升显存利用率和吞吐量。

---

## 10.2 推理优化技术

### KV Cache

自回归生成时，每生成一个新 token 都需要对整个已生成序列做注意力计算。如果不缓存，第 100 个 token 需要重算前 99 个 token 的 Key 和 Value，极其浪费。

KV Cache 把每个 token 的 Key 和 Value 向量存储起来，生成下一个 token 时直接复用，只计算新 token 的 K/V 并追加到缓存中。

缓存占用显存，长序列或大 batch 时可能消耗数十 GB。这也是 GQA 重要的原因——减少 KV 头数可以直接降低 KV Cache 显存。

### 连续批处理（Continuous Batching）

传统静态批处理：等凑够 N 个请求，一起处理，全部完成后才接收下一批。

连续批处理：每次有请求完成就立即腾出位置接收新请求，不同请求可以在不同生成步骤上同时运行。

在高并发场景下，GPU 利用率从 40-60% 提升到 80-90%+，吞吐量大幅提升。

### 投机采样（Speculative Decoding）

大模型每次只生成一个 token，速度慢。投机采样的思路：

1. 用一个**小模型**（草稿模型）快速生成 K 个候选 token
2. 用**大模型**一次性并行验证这 K 个 token
3. 接受验证通过的 token，从第一个不通过的 token 重新生成

在不改变输出质量的前提下，生成速度提升 2-3 倍。

### Prefill / Decode 分离部署

大模型推理分两个阶段：
- **Prefill（预填充）：** 处理输入 prompt，计算所有 token 的 KV Cache，计算密集型
- **Decode（解码）：** 逐个生成输出 token，带宽密集型

两个阶段的计算特征截然不同，将它们部署在不同的 GPU 集群上（Prefill 集群 + Decode 集群），各自优化，可以显著提升整体吞吐量和降低延迟。

## 10.3 训练集群工程

### GPU 选型对比

| GPU | 显存 | BF16 算力 | 互联带宽 | 适用场景 |
|-----|------|----------|---------|---------|
| **A100 80GB** | 80GB | 312 TFLOPS | NVLink 600 GB/s | 大规模预训练标准配置 |
| **H100 80GB** | 80GB | 989 TFLOPS | NVLink 900 GB/s | 最新一代，训练推理均优 |
| **H800 80GB** | 80GB | 989 TFLOPS* | NVLink 400 GB/s | 出口管制版 H100，互联带宽减半 |
| **4090 24GB** | 24GB | 330 TFLOPS | PCIe | 个人研究、小规模微调 |

*H800 的互联带宽受出口管制限制，这显著影响了大规模分布式训练的效率。

### 网络拓扑设计

**节点内通信（NVLink）：** 8 张 GPU 通过 NVSwitch 全互联，带宽极高（H100: 900 GB/s），适合张量并行（TP）。

**节点间通信（InfiniBand）：** 推荐 HDR（200 Gb/s）或 NDR（400 Gb/s），用于流水线并行（PP）和数据并行（DP）的跨节点通信。千卡以上规模通常还需要设计胖树（Fat-Tree）或蝴蝶结（Dragonfly）网络拓扑。

**存储设计：** 训练数据和检查点需要高速共享文件系统。推荐：
- **Lustre / GPFS**：工业级分布式文件系统，支持 100GB/s+ 聚合带宽
- **NVMe SSD 集群**：本地 NVMe + 并行文件系统，适合 I/O 密集场景

### 容灾与检查点策略

大规模训练动辄数百张 GPU 运行数周，硬件故障是必然事件，容灾设计至关重要。

**检查点保存频率建议：**

| 训练规模 | 建议保存频率 | 说明 |
|---------|-----------|------|
| 单机 | 每 500-1000 steps | 故障恢复成本低 |
| 多机（<64 GPU） | 每 200-500 steps | 故障影响扩大 |
| 大规模（64+ GPU） | 每 100-200 steps | 故障代价极高，频繁保存 |

**异步检查点：** 检查点写入磁盘期间不暂停训练（在后台异步完成），避免大模型检查点保存导致的训练暂停。

## 10.4 实验管理

### 训练监控关键指标

使用 WandB 或 TensorBoard 监控以下核心指标：

| 指标 | 说明 | 异常处理 |
|------|------|---------|
| **train/loss** | 训练损失 | 持续不降→检查数据和 LR |
| **train/grad_norm** | 梯度范数 | 持续 >5 → 降低 LR 或检查数据 |
| **train/learning_rate** | 当前学习率 | 确认调度器正常工作 |
| **perf/mfu** | 模型浮点利用率 | <30% → 存在通信或 I/O 瓶颈 |
| **perf/tokens_per_second** | 训练吞吐量 | 持续下降 → 可能有节点故障 |

### 成本估算公式

```
训练成本（美元）= 
  GPU 数量 × 训练时间（小时）× 单卡每小时成本
  
例：100 × A100 训练 7B 模型 1T tokens
  ≈ 100 卡 × 360 小时 × $2/卡时
  ≈ $72,000
  
（实际成本受 MFU、GPU 单价、电费等因素影响，仅供参考）
```

# 十一、前沿方向

以下几个方向是 2024-2025 年值得持续跟踪的技术演进。

---

## 11.1 长上下文

**挑战：** 将上下文从 4K 扩展到 128K 甚至 1M token，面临 O(n²) 注意力计算和 KV Cache 显存两大瓶颈。

**当前主流解决方案：**
- **RoPE 外推（YaRN/LongRoPE）：** 通过调整 RoPE 的旋转基频，让模型在不重新预训练的情况下支持更长上下文
- **长上下文微调：** 在 RoPE 扩展后，用长文档数据做继续训练（通常 10-50B tokens）
- **FlashAttention-3：** IO 感知的注意力实现，在长序列下显存节省 5-10 倍
- **Sliding Window Attention：** 只关注局部窗口，配合少量全局注意力，将复杂度降至 O(n)

**代表模型：** LLaMA 3（128K）、Gemini 1.5 Pro（1M）、Kimi（128K）

---

## 11.2 多模态训练

**主流架构：ViT + LLM**

大多数多模态大模型采用：视觉编码器（ViT）+ 连接模块 + 语言模型的结构：

1. ViT 将图像切成 patch，编码为视觉 token 序列
2. 连接模块（MLP Projector 或 Q-Former）将视觉 token 映射到语言模型的 embedding 空间
3. 语言模型将视觉 token 和文本 token 统一处理

**代表模型：** LLaVA（MLP Projector）、InstructBLIP（Q-Former）、Qwen-VL

**训练策略：** 通常先冻结 LLM 只训练连接模块，再解冻 LLM 进行端到端微调。

---

## 11.3 Test-Time Compute 扩展

训练时投入更多算力（更大模型、更多数据）是提升模型能力的传统路径。Test-Time Compute 开辟了另一个维度：推理时投入更多算力来提升单次响应质量。

**主要实现方式：**
- **长思维链（Long CoT）：** 模型在给出答案前生成完整的推理过程，步骤越充分，答案越准确
- **Best-of-N 采样：** 生成 N 个答案，选择最好的一个（需要验证器）
- **MCTS（蒙特卡洛树搜索）：** 在推理树上搜索最优路径

**代表工作：** OpenAI o1、DeepSeek-R1、QwQ

---

## 11.4 合成数据与数据飞轮

**背景：** 高质量人工标注数据越来越稀缺，而模型生成数据的质量越来越高。

**合成数据的主要用途：**
1. **SFT 数据生成**：用强大模型生成多样的指令-回答对（WizardLM、Orca 的思路）
2. **推理数据生成**：生成带思维链的数学/代码解题过程（DeepSeek-R1 的冷启动数据）
3. **偏好数据生成**：让模型生成多个回答，用规则或强模型判断优劣，构造 DPO 数据

**数据飞轮（Self-play）：**
- 强模型生成数据 → 弱模型在数据上训练变强 → 新的更强模型再生成更好的数据 → 循环
- 这是当前大模型持续改进的核心机制之一

---

## 11.5 持续学习

**挑战：** 大模型的知识是"冻结"在训练截止日期的，无法自动学习新知识。如何让模型持续更新而不忘记旧知识，是尚未完全解决的问题。

**当前主要方向：**
- **RAG（检索增强生成）：** 不改变模型权重，而是在推理时检索外部知识库，是当前工程落地最成熟的方案
- **持续微调 + 数据回放：** 定期用新数据微调，同时混入旧数据防止遗忘
- **参数隔离方法：** 为新知识分配独立的参数空间（如 LoRA 模块），避免覆盖旧知识

# 十二、典型场景训练方案

以下 5 个场景覆盖最常见的工程需求，每个场景给出端到端的配置参考。

---

## 场景一：从头预训练一个 7B 模型

**前提条件：** 有充足的 GPU 资源和数据，目标是训练一个通用基座模型。

### 资源需求估算

| 资源 | 需求 | 说明 |
|------|------|------|
| **训练 token 数** | 1T-15T tokens | Chinchilla 最优 140B，实践中 1T+ 更好 |
| **GPU 数量（A100）** | 64-256 卡 | 视时间预算和 token 数量而定 |
| **训练时间** | 2-8 周 | 64 卡 × 4 周 ≈ 1T tokens |
| **存储** | 100TB+ | 原始数据 + 清洗数据 + 检查点 |
| **预计成本** | $50K-$500K | 根据规模差异极大 |

### 推荐技术栈

```yaml
# 推荐配置（64 × A100）
架构: LLaMA-3 style（RoPE + GQA + SwiGLU + RMSNorm）
并行策略: TP=8（节点内）+ DP=8（节点间）
框架: Megatron-LM 或 DeepSpeed + FSDP
精度: BF16（参数）+ FP32（梯度）
优化器: AdamW（β1=0.9, β2=0.95, wd=0.1）
学习率: 3e-4（峰值），Warmup 2000 steps + Cosine Decay
批大小: 2M-4M tokens/step（梯度累积实现）
序列长度: 4096（前期），8192（后期）
```

### 关键里程碑

| 进度 | 里程碑 | 检查内容 |
|------|-------|---------|
| 1% | 初步验证 | Loss 是否正常下降，MFU 是否达标（>40%） |
| 10% | 能力涌现检查 | 开始出现基础语言能力，Loss 曲线平滑 |
| 50% | 中期评估 | 跑完整 benchmark，确认各维度能力正常发育 |
| 80% | Cooldown 准备 | 切换到高质量数据 Cooldown 阶段 |
| 100% | 预训练完成 | 保存检查点，准备后训练 |

---

## 场景二：垂直领域继续预训练（Domain-Adaptive Pre-training）

**典型需求：** 有一个通用基座模型（如 LLaMA 3 8B），想让它更擅长医疗、法律、金融等垂直领域。

### 什么时候用继续预训练（vs 直接微调）

| 情况 | 建议 |
|------|------|
| 领域词汇/表达方式与通用语料差异很大（医学术语、法律条文） | **继续预训练** |
| 有大量领域无标注文本（>10B tokens） | **继续预训练** |
| 只有少量标注数据（<100K 条） | **直接 SFT 微调** |
| 时间/资源紧张 | **直接 SFT 微调** |

### 数据配比与训练策略

```
推荐数据混合比例（参考）：
  领域数据：70-80%（你的目标领域文档）
  通用数据：20-30%（防止遗忘通用能力）

训练参数（在 SFT 参数基础上降低）：
  学习率：1e-4 ~ 5e-5（比从头预训练低一个量级）
  训练 token 数：10B-100B（领域数据规模决定）
  序列长度：与基座模型保持一致
```

### 防止遗忘的关键手段

1. **通用数据回放**：始终混入 20-30% 通用数据，最重要的防遗忘手段
2. **低学习率**：学习率越高，遗忘越快
3. **验证通用能力**：每隔一段时间用 MMLU 等通用 benchmark 监控是否退化

## 场景三：基座模型 SFT + 对齐（最常见场景）

**典型需求：** 拿到一个开源基座模型（如 LLaMA 3 8B），做 SFT + DPO 对齐，变成一个可用的对话助手。

### SFT 阶段

**需要多少数据？**

| 数据量 | 预期效果 |
|--------|---------|
| 1K 条（精选） | 基础指令跟随，能完成简单任务 |
| 5K-10K 条 | 良好的通用对话能力 |
| 50K-100K 条 | 接近商业模型的通用能力 |
| 500K+ 条 | 顶级通用能力，需要非常高的数据质量 |

**推荐 LoRA 配置（8B 模型）：**

```python
lora_config = {
    "r": 16,
    "lora_alpha": 32,
    "target_modules": ["q_proj", "k_proj", "v_proj", "o_proj",
                       "gate_proj", "up_proj", "down_proj"],
    "lora_dropout": 0.05,
}

training_args = {
    "learning_rate": 2e-4,
    "num_train_epochs": 3,
    "per_device_train_batch_size": 4,
    "gradient_accumulation_steps": 4,
    "warmup_ratio": 0.03,
    "lr_scheduler_type": "cosine",
}
```

**SFT 阶段时间估算（8B，10K 条数据，单机 8×A100）：** 约 1-2 小时

### DPO 对齐阶段

**偏好数据构造方法：**
1. 对每个 prompt，用 SFT 模型生成 4-8 个候选回答
2. 用 GPT-4 或人工对回答进行排序
3. 选取最好的作为 chosen，最差的或明显有问题的作为 rejected

**推荐配置：**

```python
dpo_config = {
    "beta": 0.1,        # KL 惩罚系数，越大越保守
    "learning_rate": 5e-5,  # 比 SFT 更小
    "num_train_epochs": 1,  # DPO 通常只需 1 个 epoch
}
```

**全流程成本估算（8B 模型，单机 4×80GB A100）：**
- SFT（10K 条）：~2 小时，~$10
- DPO（5K 对）：~1 小时，~$5
- **总计：约 3 小时，约 $15**

## 场景四：资源受限下的高效训练（单机 4×24GB）

**典型需求：** 只有 4 张消费级 GPU（如 RTX 3090/4090），想微调一个 7B 模型。

### 完整 QLoRA 配置

```python
# 显存分配（每张 24GB）：
# 模型权重 4-bit：~4GB
# LoRA 参数 BF16：~0.5GB
# 激活值：~3GB（梯度检查点后）
# 优化器状态：~2GB
# 预留缓冲：~3GB
# 合计：~12.5GB，4 张卡均可承受

from transformers import BitsAndBytesConfig
bnb_config = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_use_double_quant=True,
    bnb_4bit_quant_type="nf4",
    bnb_4bit_compute_dtype=torch.bfloat16,
)

training_args = {
    "per_device_train_batch_size": 1,
    "gradient_accumulation_steps": 16,  # 等效 batch=64
    "gradient_checkpointing": True,      # 时间换空间
    "optim": "paged_adamw_8bit",         # 8-bit 优化器，节省显存
    "max_grad_norm": 1.0,
    "learning_rate": 2e-4,
    "num_train_epochs": 3,
}
```

### 显存优化组合拳

同时开启以下优化，显存需求可降低 60-70%：

| 优化手段 | 显存节省 | 速度影响 |
|---------|---------|---------|
| 4-bit 量化（NF4） | ~60% | 几乎无影响 |
| 梯度检查点 | ~40% | -30% 速度 |
| 8-bit AdamW | ~50% 优化器显存 | 几乎无影响 |
| gradient_accumulation | 等效更大 batch | 无影响 |

### 常见 OOM 解决方案

- **OOM 报错**：减小 `per_device_train_batch_size` 到 1，增大 `gradient_accumulation_steps`
- **仍然 OOM**：减小 `max_seq_length`（如从 2048 降到 1024）
- **还是 OOM**：降低 LoRA 的 `r`（如从 16 降到 8），减少目标层
- **终极手段**：开启 CPU offloading（速度会慢 3-5 倍，但能运行）

### 性能预期

单机 4×RTX 4090，QLoRA 微调 7B 模型，10K 条数据：
- 训练时间：约 2-4 小时
- 最终效果：接近全参数微调的 85-90%

## 场景五：增强推理能力（数学 / 代码）

**典型需求：** 基础对话能力已经很好，但数学推理或代码能力不足，想专项提升。

### 为什么通用 SFT 对推理提升有限

通用 SFT 数据以"最终答案"为主，模型看到的是"问题→答案"的映射，但没有学到"如何一步步推理"的过程。对于复杂数学题，直接预测答案正确率极低。

**解决方案：** 用带有**详细推理过程**的数据训练，让模型学会"思考链"。

### 数据飞轮：合成数据 + 规则验证

```
数据飞轮流程：

1. 收集数学/代码题目（GSM8K、MATH、LeetCode 等）
2. 用强大模型（GPT-4/o1）生成详细解题过程
3. 用代码执行器或数学验证器检验答案正确性
4. 只保留答案正确的 <题目, 思维链, 答案> 三元组
5. 用这些数据做 SFT → 得到更强的模型
6. 用新模型生成更多数据（self-play），循环
```

### GRPO 训练配置

```python
# 奖励函数设计（数学场景）
def reward_fn(response, ground_truth):
    # 格式奖励：有 <think> 标签
    format_reward = 0.1 if "<think>" in response else 0
    # 正确性奖励：答案正确
    answer = extract_answer(response)  # 提取最终答案
    correctness_reward = 1.0 if answer == ground_truth else 0
    return format_reward + correctness_reward

# GRPO 超参数
grpo_config = {
    "num_generations": 8,      # 每个问题生成 8 个回答
    "learning_rate": 1e-6,     # 比 SFT 更小
    "kl_coef": 0.01,           # KL 惩罚
    "temperature": 0.8,        # 采样温度
}
```

### 评估指标与效果预期

| 基线 | GSM8K | MATH |
|------|-------|------|
| 7B SFT（通用）| ~60% | ~15% |
| 7B SFT（数学数据）| ~75% | ~30% |
| 7B GRPO（+规则奖励）| ~85% | ~45% |

通过合成数据 + GRPO，7B 模型的数学能力可以超越早期版本的 GPT-3.5。

## 技术选型决策树

```
我需要训练/微调一个大模型
│
├── 是否有自己的基座模型？
│   ├── 否 → 选择开源基座（LLaMA 3 / Qwen / Mistral）
│   └── 是 → 继续向下
│
├── GPU 资源有多少？
│   ├── 单机 ≤4 张消费级 GPU（≤24GB）
│   │   └── QLoRA 微调 7B/13B（见场景四）
│   │
│   ├── 单机 8 张 A100/H100（≤640GB）
│   │   ├── 全参数微调 7B 或 13B
│   │   └── LoRA 微调 70B
│   │
│   └── 多机集群（64+ GPU）
│       ├── 继续预训练 → Megatron-LM + 3D 并行
│       └── 全参数微调 → DeepSpeed ZeRO-3
│
├── 任务类型是什么？
│   ├── 通用对话对齐 → SFT + DPO（见场景三）
│   ├── 垂直领域知识增强 → 继续预训练 + SFT（见场景二）
│   ├── 数学/代码推理 → SFT（思维链数据）+ GRPO（见场景五）
│   └── 从头训练 → 全流程预训练（见场景一）
│
└── 部署方式？
    ├── 在线服务高并发 → vLLM
    ├── 延迟极敏感 → TensorRT-LLM
    └── 本地/端侧 → llama.cpp + GGUF Q4_K_M
```

## 结语

训练一个大语言模型，是数据、算法、系统、工程多个维度的综合工程：

- **数据是地基**：架构和算法无法从低质量数据中训练出高质量模型
- **架构是框架**：合适的架构决定能力上限和推理成本
- **预训练是建造**：算力和数据在这里转化为模型的世界知识
- **对齐是装修**：把"知识丰富但行为粗糙"的模型改造成真正有用的助手
- **部署是交付**：让训练成果以合理的成本触达真实用户

每个环节的决策都需要在具体约束下做出权衡，没有通用最优解。
